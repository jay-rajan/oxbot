  3. Docs: commit the architecture and plan pages that are safe to be public. Keep the business pages private (home-cloud: trial price and caps; legal): add them to a local-only ignore (.git/info/exclude), not the public repo.

The branches stay in git, so nothing is lost. The one untracked folder (rebrand's screenshots) is moved to the settings worktree first. Keep settings and react.
  5. Old branch names: keep them for now; deleting merged names is optional and can wait.

After this: main = everything built so far, the editor shows only real work in progress, and two worktrees remain (settings, react).

2 · How oxbot is built

One program runs on the home computer (the Mac). It serves the app's page to the Mac window and to phones, runs the bots, and is the only thing that talks to the internet. Phones are just screens: they never store chats and never run bots.

5 · Backups: today and later

Today

  • Before a schema upgrade that rebuilds tables, oxbot copies the whole database next to itself (oxbot.db.vN.bak, made with SQLite's VACUUM INTO, which gives one consistent file).
  • Time Machine covers the folder if the user has it on. A copy taken while oxbot is writing can be inconsistent, though, and Time Machine skips nothing on purpose.
  • No regular backup, no off-computer copy. A lost or broken Mac loses every chat.

Planned, in three layers

LayerWhatHow
1 · Daily snapshot on the MacThe database plus every bots/ folder, once a day, keep 7 daily and 4 weekly.SQLite's online backup (VACUUM INTO) to Backups/, then the bot folders copied with it, into one dated folder. Safe while oxbot runs. Settings → General: "Last backup: today 3:00".
2 · Encrypted copy off the Mac (with the oxbot service)The same snapshot, encrypted on the Mac before it leaves.Encrypted with a key only the home has (a recovery phrase the owner writes down). The service stores sealed blobs it can't read, in object storage. Only changed pieces are sent each day. Off by default; the owner turns it on.
3 · RestoreNew Mac, or roll back.Install oxbot, choose "Restore from backup", enter the recovery phrase. Devices pair again (their keys stay on the old Mac on purpose), and websites need signing in again (cookies aren't backed up).

Never in a backup: the OpenRouter key (Keychain; reconnect after a restore), browser cookies and passwords, device keys. Restored chats keep their personal details, so layer 2 must be end-to-end encrypted, not just "encrypted at rest" by a cloud provider.

6 · What's the best database for production?

On the home computer: keep SQLite. It's the right tool here, not a stopgap. One program writes, one home's data is small (megabytes to a few GB), and there's nothing for a family to install, run or update. Postgres on every Mac would add a server process, upgrades, and a new way for the app to break. Apple Notes, Photos and Messages all run on SQLite for the same reason.

For the oxbot service (trial keys, accounts, device connections, backup records): Postgres, managed (for example on AWS RDS or Neon; no Google, per the rules). Many writers, many homes, it needs real users and roles, point-in-time recovery and replicas. It never holds chats, only accounts and sealed backup records; the encrypted blobs go to object storage (S3 or Cloudflare R2).

DataWhereWhy
Chats, reports, people, devices, activitySQLite on the home computerPrivate by design; works offline; nothing to run.
Accounts, trials, billing, which homes existPostgres (oxbot service)Many writers, needs backups and replicas.
Encrypted home backupsObject storage (S3 / R2)Cheap, large, the service can't read them.

Worth fixing in the SQLite schema before launch

  • A bots table: today a bot exists only as a folder, so nothing in the database can check that a bot value is real. A table (id, created, deleted) would allow foreign keys and clean deletes.
  • Foreign keys and STRICT tables for the core tables (people, gates, profiles, bot_members, schedules), so bad rows are refused instead of found later.
  • Retention for the growing logs (model_calls, relay_log, loop_messages of closed sessions), like net_log's 30 days.
  • Big JSON in events.body is fine at a home's scale; keep large content (files, page snapshots) on disk, as now.
