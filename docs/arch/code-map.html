oxbot Code Map

The lay of the land before going module by module: what runs where, what each crate does, how one message travels, and the order to read things in.

In one paragraph. One Mac (the home computer) runs everything. The Tauri app starts the same server as oxbot serve: an axum WebSocket server in front of the Hub, which owns every bot. Each bot is driven by its own Codex CLI process (codex app-server, talked to over JSON-RPC). Codex never touches the network or your machine directly: its model calls can only go to oxbot's relay on 127.0.0.1, which strips identity and personal details and forwards to OpenRouter; its tool calls come back into oxbot's tool service, where the gate asks the hub's policy before anything runs (and shows an approval request when a step changes something). Browsing happens in a hidden, signed-in Chrome driven by chrome-devtools-mcp. History lives in SQLite (oxbot.db), and every change is broadcast to the chat page on the Mac and to Android phones through the TLS device door.

Code names differ from what the app says. Keep this list handy:

Farm = home computer Gate = device (phone) Herder = Assistant engine = what runs a bot (Codex today) card = approval request rule = Always allow taint = has read untrusted text

SafetyThe lines oxbot never lets Codex cross

These are the design's load-bearing rules. When you read a module, ask which of these it enforces.

No tool without a Permit

Only GateCheck::check in oxbot-loop/src/gate.rs makes a Permit, and tools need one to run. A lost answer counts as no.

oxbot decides, not the bot

oxbot-core/src/policy.rs (2,462 lines) maps every browser step to run, run-and-log, approval request or refuse.

One way out for models

Codex's only model provider is the relay. Which bot a request is for comes from its token and oxbot's own record, never from what Codex sends.

Untrusted text is marked

Web pages, files and other bots' replies set a taint (hub/taint.rs). A tainted Assistant asks before tasking a private bot.

Phones are pinned and scoped

The door is TLS-only on 7879 with a pinned certificate, open only on listed networks. A device always acts as its person.

Strict compile rules

unsafe_code = "forbid", clippy pedantic, no unwrap/expect outside tests, thiserror in libraries.

PlanSuggested order for your module questions

Bottom-up, following the message path, so each module only uses things you've already seen.

  1. Vocabulary: oxbot-protocol and oxbot-engine. Small, pure types. Learn ClientMsg, ServerMsg, EngineEvent and the Engine/Session traits first.
  2. The store: oxbot-core/src/store/. The schema and migrations.rs tell you what oxbot remembers.
  3. The Hub: hub/mod.rs then hub/turns.rs. How a message reaches an engine, and how events get stored and broadcast.
  4. The Codex engine: oxbot-codex. The supervisor, the JSON-RPC, and how a turn runs.
  5. Tools and the gate: oxbot-loop (service.rs, gate.rs, tools/, page/). The biggest idea in the code.
  6. Policy and approvals: policy.rs, hub/approvals.rs, rules.rs, taint.rs.
  7. Models: oxbot-relay, then the gateway in oxbot-loop, then oxbot-llm. Privacy, routing, limits.
  8. The browser: oxbot-browser and hub/browsers.rs. Shared Chrome and turn-taking.
  9. The edges: oxbot (server, door), oxbot-gate, app/src-tauri, the chat page.
  10. Features on top: schedules, reports, the Assistant's team tools, compare and practice runs, attachments.
  11. Testing: oxbot-e2e and how its stand-ins mirror the real pieces.
