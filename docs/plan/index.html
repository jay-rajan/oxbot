oxbot

GrokBot-style bots that run on your Mac with Claude, which you reach from an Android phone on your home Wi-Fi. Bots browse the web through a Chrome profile of their own, headless. Codex comes next.

What you'll have at the end of v1

  • Open oxbot on your Android phone. It finds your Mac on Wi-Fi by itself.
  • Scan a QR code once to pair. After that, the phone just connects.
  • See your bots like chats in a messenger. Talk to one, and watch Claude work live.
  • Bots have their own instructions and schedules ("every day 8am"), and keep running when the phone is off.
  • Bots can use the web through your oxbot Chrome profile, with your logins, invisibly in the background.
  • Data goes only to Anthropic. Nothing passes through any other company's server.

How it fits together

Chrome, without setup per bot

Every bot gets the browser automatically. You never configure it per bot.

  • One-time login: oxbot chrome login opens a visible Chrome window on the oxbot profile. You sign in to the sites the bots need (Substack, Gmail, …) yourself, then close it.
  • After that it's automatic: when a bot needs the web, oxbot starts one headless Chrome on that profile, listening only on 127.0.0.1. Every Claude run is handed the browser tool (Google's chrome-devtools-mcp) already pointed at it. Each bot works in its own tab, and Chrome shuts down when idle.
  • Many bots, one browser: sharing one running Chrome avoids the "profile already in use" lock you'd hit with a Chrome per bot.
  • When a site needs you (login expired, CAPTCHA): the bot stops and your phone shows "needs you". Run oxbot chrome show to bring that tab up visibly, sort it out, and the bot carries on. Bots never type your passwords.
  • Why not your everyday Chrome profile: it's open and locked while you use Chrome, and Chrome 136+ blocks automation on the default profile. A separate profile also keeps the bots away from your banking and personal tabs.
  • Privacy: the browser tool's Google usage stats, performance lookups and update checks are switched off (--no-usage-statistics, --no-performance-crux, CHROME_DEVTOOLS_MCP_NO_UPDATE_CHECKS). The pages a bot visits do see the visit; that's the job.

Android app

Tauri 2 (recommended)

Rust inside the phone app too. The server and the app share one oxbot-protocol crate, so a message type is defined once. You keep learning Rust on both sides. QR scanning comes from Tauri's official barcode plugin. Networking and pinned TLS live in Rust; a small Kotlin plugin handles Wi-Fi discovery (Android's NsdManager). The same code can become the iPhone app later.

Kotlin + Jetpack Compose

Android's native toolkit: discovery and certificate pinning are built in, and it's the smoothest Android experience. But it's a second language, protocol types get written twice, and iPhone would be a separate app.

Testing and the Play Store

  • Testing needs no account: turn on USB debugging on your phone, and cargo tauri android dev installs it directly.
  • Play Store: a one-time $25 developer account. New personal accounts must first run a closed test with at least 12 testers for 14 days in a row before publishing (Google). Start gathering testers early.
  • Mac setup (I'll walk you through it): Android Studio for the SDK and NDK, and Rust's Android targets.

Standards I'll hold to

  • Gate before every step is done: cargo fmt --check, cargo clippy --workspace --all-targets -- -D warnings, cargo test --workspace.
  • Lints in one place: unsafe_code = "forbid", clippy pedantic on warn, and unwrap_used/expect_used warned outside tests.
  • Errors: thiserror enums in libraries; anyhow only in the binary. No panic! on bad input.
  • Docs: //! on every crate, /// on public items, and #![warn(missing_docs)] in libs.
  • Tests: unit tests in mod tests, integration tests in tests/, and recorded claude output as fixtures, so tests never spend your subscription.
  • Logging and naming: tracing for logs (no println! in the server), and the API naming guidelines (new, from_*/into_*, is_*).
  • Licence: dual MIT / Apache-2.0, the Rust community norm.

A test, as you'd read it

name   = "Someone else's private bot is locked"
covers = ["crates/oxbot-core/src/hub.rs", "crates/oxbot/src/server.rs", "crates/oxbot/ui/**", "private"]
as     = "Ann"            # connect as a Gate person (or the Farm)

[[step]] do = "open"                      shot = "sidebar"
[[step]] expect = "Bank · by Sam"         lock = true
[[step]] do = "click"  text = "Bank"      shot = "locked chat"
[[step]] expect = "Sam's private bot"     expect_not = "balance"   # no real chat text on screen
[[step]] expect_disabled = "Message"

Steps are: open, click (by visible text), type, send, wait for, expect / expect not, expect disabled, and shot (screenshot). Each step records what it did, how long it took, and a screenshot.

How a run works

  1. Read the change: what changed against main (or the PR, with gh), plus the commit messages and PR description, to state its intent in one line.
  2. Pick tests: a test runs when the change touches its covers list. A small smoke set (open the app, chat with Herder, Settings) always runs. /pr_test all runs everything. The report says why each test was picked or skipped.
  3. Changed tests: if the change edits a test, I check the stated intent. If the intent says so (for example "rename New bot to +"), the new test is used. If not, the run uses the old test from main, and the report flags the edit as unexplained. A change can't quietly weaken a test.
  4. Fresh oxbot: build it, copy the seed into a new throwaway folder, apply seed.sql to a new SQLite database, and start oxbot serve on a free local port. Claude is the scripted stand-in, so runs are free, fast and the same every time. The browser is a hidden Chrome with its own empty profile. Nothing touches your real oxbot, your sign-ins or the network.
  5. Drive the page: the runner speaks to Chrome directly (the same DevTools link oxbot already uses), runs each step, and takes a screenshot per step.
  6. Compare: each screenshot is compared with its approved baseline. A failed step is broken; a screen that looks different but passed is changed, shown side by side for you to approve or not. Approving updates the baseline.
  7. Fix: for anything broken, I find the cause and fix the code (not the test), then run the failed tests again, then the whole picked set. If the change meant to alter that behavior, I update the test and say so in the report.
  8. Report artifact: one page per run: the intent, the tests picked and why, then each test with its steps, a screenshot per step, timing, and Pass / Broken / Changed flags; what I fixed, with the diff; and anything left for you.

How it works

  • Farm: the one Mac that runs the bots, Claude Code (on its owner's Claude plan) and the Chromes, and keeps all chats. Everything stays on it.
  • Gates: a laptop or phone shows the same app but runs no bots. On first open the app asks: "Make this Mac the Farm" or "Connect to a Farm". A Gate finds the Farm on home Wi-Fi, pairs once with a code (QR on phones), and from then on connects encrypted, with the Farm's certificate pinned. No relay, no cloud.
  • People: each Gate is paired as one person. Their name goes on their messages and the bots they make, in their color.
  • Shared bots (the default): everyone sees and uses them. They use the home Chrome, so a site signed in there works for every shared bot (today's behavior).
  • Private bots: the creator can make a bot private. Everyone still sees its name with a lock, but only its creator can open it: for anyone else the chat shows as blurred placeholder lines (nothing of the real chat is sent to them), the message box is off, and Herder tells them it's private and won't give it tasks for them. (Your call, 2026-10-30: "you can still see the bot name. but just that the bot is locked and the converstation blurred.") A private bot uses only its owner's own Chrome, never the home Chrome or anyone else's. If Sam's private bot needs Gmail, Sam signs in to Gmail in Sam's Chrome, even if Gmail is already signed in at home. That's the "logging in twice".
  • The Farm can do anything: on the Farm itself, the owner sees every bot (private ones marked private), and can open, rename, make shared, or delete any of them. The Gates don't get this power, even the owner's own phone. Everyone in the house should know the Farm owner can read private chats.
  • Herder: shared by everyone. A bot Herder creates belongs to whoever asked. Herder only works with a person's private bots when that person is the one asking.
  • Signing in from a Gate: the sign-in window is a Chrome window on the Farm, so a person on their phone can't see it. oxbot shows that page live on the Gate (a stream from Chrome) and passes their taps and typing back. The password goes from their phone straight to their own Chrome over the paired, encrypted link. The bot is paused the whole time and never sees it.
  • Sign-ins in Settings: "Your sign-ins" (your Chrome) and "Home sign-ins" (the home Chrome), each with icons, Open and Sign out. Bots made before this become shared bots by the Farm owner.

Was: Your words: "can i make installation easy for others … installing claude i mean. and the mcp". Today a friend has to install Claude Code and Node.js by hand before oxbot works.

What a friend does

  1. Opens oxbot. The setup screen lists what's missing.
  2. Presses Install Claude Code. oxbot runs Anthropic's own installer (the native build from claude.ai, the same as curl -fsSL https://claude.ai/install.sh | bash) and shows its progress. No Terminal, no Node.
  3. Presses Sign in to Claude. oxbot runs claude auth login, which opens Claude's sign-in page in their normal browser. They sign in with their own Claude plan.
  4. oxbot checks with claude auth status and the setup screen turns green. Done: the browser tool is already inside oxbot.

How

  • Claude Code: a button, not a silent install, because it runs a program from the internet (Anthropic's). oxbot fetches the installer only from https://claude.ai and shows what it's doing. If Claude Code is already installed, nothing changes.
  • Sign-in check: claude auth status --json replaces today's guess from files. oxbot never sees the password or token.
  • The browser tool (MCP): shipped inside oxbot.app: chrome-devtools-mcp at a fixed version, plus the small Node runtime it needs. No npm at first run, nothing fetched from npm, and friends don't install Node. The app grows by about 60–90 MB (Apple chip + Intel).
  • Chrome: still the friend's own Google Chrome. oxbot can't install it, so the setup screen links to google.com/chrome.
  • Updates: a new oxbot release brings a newer browser tool. Claude Code updates itself as it does today.

What changes in the code

  • oxbot/setup.rs: install_claude() (download from claude.ai, run, stream progress), sign_in_to_claude() (claude auth login), sign-in check via claude auth status.
  • oxbot-protocol: ClientMsg::InstallClaude, ClientMsg::SignInClaude, ServerMsg::SetupProgress.
  • oxbot-browser: ToolsConfig points at the bundled tool and Node inside the app; npm only for oxbot serve dev runs.
  • scripts/make-dmg.sh: fetch and pin Node (both chips) and chrome-devtools-mcp into the app's resources, with checksums.
  • Setup screen: Install and Sign in buttons with progress. The friends guide gets shorter. The C4 architecture page gets updated.

What the Assistant can do

  • Create a bot: it picks a name and writes the instructions from your chat, then a card asks you: "Assistant wants to create Gmail Checker", with the instructions shown. Nothing is created until you press Create.
  • See the team: list every bot, what it's for, and whether it's working.
  • Give a bot a task: it sends the bot a message. The message shows in that bot's chat, marked "from Assistant", so you can follow along. That bot still asks you before any send, post, delete or buy, and still asks you to sign in.
  • Read the reply: it waits for that bot to finish and brings the answer back to your chat with the Assistant.

Limits

  • Only the Assistant has these tools. Other bots can't create bots or message each other, so there are no loops.
  • The Assistant can't delete, rename or change bots. You do that.
  • It can't send a task to itself, and it waits for at most one task at a time per bot.
  • The Assistant is pinned at the top of the sidebar and can't be deleted. A new oxbot gets one automatically.

What changes in the code

  • oxbot-core/tools.rs: four more tools on the built-in oxbot tool server, offered only to the central bot.

  • oxbot-protocol: a new card kind CreateBot {name, instructions}; BotInfo.central.
  • Prompt: the Assistant's system prompt explains its team tools and that it should create a bot only when a job will repeat or needs its own memory.
  • UI: the Create card; the Assistant pinned first with a small "central" mark.
  • Tests with a fake Claude: create after OK, nothing on Deny, a task round trip, and other bots not offered the tools. Then a real run with Haiku. The C4 architecture page gets updated.

How it works

  • Which sites show: the sites you signed in to through oxbot's sign-in window, recorded when a sign-in finishes. oxbot also checks the shared browser still holds sign-in cookies for each one, and drops it from the list if not. Not every site the bots visit: those leave tracking cookies and would clutter the list.
  • One name per site: grouped by the site's main domain, so a sign-in at accounts.google.com shows as google.com. Uses the public list of web domains built into oxbot, with no network calls.
  • Open: opens that site in the visible Chrome window, the same window as sign-in. Close it to go back to hidden.
  • Sign out: asks once more, then deletes that site's cookies and stored data from the shared browser (DevTools Storage.clearDataForOrigin and Network.deleteCookies). Other sites stay signed in. If a bot is using the browser, it says so and you try again in a moment.
  • Gear: opens Settings, which stays as it is: General and Activity tabs, and "Sign out of all sites".

What changes in the code

  • oxbot-protocol: ServerMsg::Sites, ClientMsg::OpenSite, ClientMsg::SignOutSite, SiteInfo {site, signed_in_ms}.

Done: sign in on demand

Today a bot that hits a sign-in page stops and asks you to run oxbot chrome login. Instead, the bot asks for the sign-in itself, and the task carries on once you're in.

StepWhat happens
1. Bot hits a sign-in pageIt calls a new oxbot tool, request_sign_in(url, why), for example Gmail's sign-in page, "to search your September mail".
2. oxbot shows you the pageThe oxbot Chrome comes up as a visible window on that exact page. The app (and later your phone) shows "Gmail needs you to sign in", with the reason and a Done button.
3. You sign inYou type your password and 2-step code in the real Google page. Google remembers it in the oxbot profile.
4. The bot carries onPress Done, or close the tab. The tool returns "signed in", and the bot retries and finishes the task. If you don't respond within 10 minutes, it says so and stops.

Why not let the bot type the password?

  • Anything the bot types passes through Claude, so your password and codes would be sent to Anthropic. That breaks your data rule.
  • Google usually blocks sign-ins from automated browsers ("This browser or app may not be secure"), and 2-step codes need you anyway.
  • Possible later, for simple sites: oxbot itself fills a saved password from your Mac's Keychain, so the model never sees it. It won't work for Google, so it's not worth building first.

How it's built

  • oxbot mcp: a small tool server built into the oxbot binary (MCP over stdio). Every bot gets it next to the browser tool. It passes the request to the running oxbot over the WebSocket.
  • Protocol: new messages SignInNeeded {bot, url, why} (server to app) and SignInDone (app to server).
  • Bot prompt: "If a site needs sign-in, call request_sign_in with the page and the reason. It shows the page to the user and waits."
  • Tests: the tool server over stdio; a fake bot asks, a fake app answers Done; and the timeout.

Milestone 3 overview: the phone link, tested with a stand-in phone

PieceWhat I'll build
EncryptionOn first run, oxbot makes its own certificate (rcgen) and keeps it in its data folder. The server listens on your Wi-Fi with TLS (rustls). Clients trust only that certificate's fingerprint (pinning), so no certificate authority is involved.
Pairingoxbot pair prints a QR code in the terminal: oxbot://pair?host=…&port=7878&fp=…&code=…. The code works once and expires after 5 minutes. The phone trades it for its own random token. The server stores only a hash of the token.
Devicesoxbot devices lists paired phones and when each was last seen. oxbot devices revoke <name> cuts one off immediately. Every connection must sign in with its token first; unknown connections are closed.
DiscoveryThe server announces _oxbot._tcp on Wi-Fi (mdns-sd) with its name and fingerprint, so the app can list it without typing an IP.
Stand-in phoneoxbot connect "oxbot://pair?..." does exactly what the app will: pairs, saves its token, connects over TLS with pinning, then chats. This proves the whole phone flow before any Android code.
Laptop chatoxbot chat keeps working on the laptop and signs in with a local token file only your user can read.

  • macOS will ask once: "Allow incoming network connections?" for oxbot the first time it listens on Wi-Fi, and possibly a Local Network prompt for discovery. Click Allow.
