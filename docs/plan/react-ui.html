Move the app's screens to React

Today every screen lives in one hand-written page of about 3,300 lines: HTML, CSS and JavaScript together. This plan rebuilds it as React components in TypeScript, one per piece of the design system. Users see no change, and every behavior and automated test is kept.

1 · Why

TodayWith React + TypeScript
One 3,300-line file. Every change means finding the right spot among hundreds of functions.About 60 small files, one per screen or piece (Sidebar, Composer, SiteRow, SettingsTabs…), matching the design system.
Each screen redraws itself by hand when a message arrives. It's easy to forget one, which is where most UI bugs come from.Screens are drawn from the app's state, so a change shows everywhere it should.
Messages from the server are untyped. A renamed field breaks silently.Message types are generated from the Rust protocol, so a rename stops the build.
Inline scripts, so no strict security policy can be set on the page.Scripts load from files, so the page can forbid any other script (a strict Content-Security-Policy). That's a real gain against injected content.
No unit tests for screen logic.Unit tests for the state rules (Vitest), plus the end-to-end tests we have.

2 · What it's built with

  • React 18 and TypeScript, built with Vite into plain files: one script, one stylesheet, index.html.
  • No outside requests, as today: the built files go inside the oxbot program (as index.html does now), with no CDN and no fonts from the web.
  • Few packages: react and react-dom at run time. Vite, TypeScript, Vitest and ts-rs only while building. The exact versions are locked, and installs use the lockfile (npm ci).
  • Types from Rust: the protocol crate derives TypeScript types (ts-rs), so the page and the server always agree.
  • State: one store fed by the server's messages (a reducer per area: bots, chat, cards, settings, people, websites, activity). Components read the parts they need. No extra state library.
  • Styles: the design system's tokens become one tokens.css, and each component has a small CSS file. The design system page and the app share the same values.

4 · How it gets there

  1. Set up: the Vite project, the generated protocol types, the socket and the store, and a page that connects and shows the bot list. Built files are embedded the same way index.html is today.
  2. Port screen by screen, keeping every element id, label and message the end-to-end tests look for: sidebar, then chat and composer, cards, bot settings and New bot, Welcome, Settings (the new four-tab version), reports, Compare.
  3. Parity: the whole end-to-end suite passes on the React page with no unexplained screen changes. You approve any changed screens.
  4. Switch: the built React page replaces the hand-written one, and the old file is deleted. The strict security policy goes on the page.
  5. Builds: make-dmg.sh and the Android build run the UI build first. The tests check that the built files match the sources.

Your phones and the Mac app use the same page, so they all move together. Nothing changes on the server or in stored data.
