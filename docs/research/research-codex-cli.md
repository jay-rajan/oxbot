# oxbot research: OpenAI Codex CLI backend

Researched 2026-10-27 against **codex-cli 0.148.0** (installed via npm at `/opt/homebrew/bin/codex` → Node wrapper → native Rust binary `.../@openai/codex-darwin-arm64/vendor/aarch64-apple-darwin/bin/codex`). The machine is logged in with ChatGPT (Plus plan, as shown in `account/rateLimits/updated`).

Legend: **[V]** = verified locally (help output, schema generation or a real call). **[D]** = from official docs. **[S]** = from the source/binary. **[3P]** = third-party source.

Note: `developers.openai.com/codex/*` now 308-redirects to `learn.chatgpt.com/docs/*`.

Real model calls used: 3 (exec, exec resume, app-server inject + turn). Artifacts are in the scratchpad:
- `codex-sample.jsonl`, `codex-sample-resume.jsonl`: real `exec --json` output
- `appserver-transcript.jsonl`: real app-server JSON-RPC wire log

## 1. Non-interactive mode: `codex exec --json`

### Flags [V] (from `codex exec --help`)

- `--json`: JSONL events on stdout.
- `-o, --output-last-message <FILE>`: writes the final message to a file.
- `--output-schema <FILE>`: JSON Schema for the final answer.
- `--ephemeral`: don't write a rollout file.
- `--skip-git-repo-check`: allow running outside a git repo.
- `-C/--cd <DIR>`, `--add-dir <DIR>`: working root and extra writable directories.
- `-s/--sandbox read-only|workspace-write|danger-full-access`
- `-m/--model`, `--oss`, `--local-provider lmstudio|ollama`, `-p/--profile`, `-c key=value`
- `--enable/--disable <feature>`
- `--ignore-user-config`: skip `$CODEX_HOME/config.toml`; auth still comes from `CODEX_HOME`.
- `--ignore-rules`
- `--approve-for-me`: routes approvals to automatic review in the workspace-write sandbox.
- `--dangerously-bypass-approvals-and-sandbox` (alias `--yolo`)
- `-i/--image`

Notes on these flags:
- **`exec` has no `-a/--ask-for-approval` flag** in 0.148 (only the top-level TUI has it). Use `-c approval_policy="never"` instead.
- **`--full-auto` no longer exists** in 0.148.

### Prompt input

- The prompt comes from the argument, or from stdin if no argument is given (or the argument is `-`).
- If stdin is piped **and** a prompt is given, stdin is appended as a `<stdin>` block.
- **Gotcha [V]:** with an inherited open stdin, exec prints `Reading additional input from stdin...` and waits. Always spawn with `stdin = Stdio::null()`, or write the prompt to stdin and then close it.
- Progress goes to stderr. Without `--json`, only the final message goes to stdout [D].
- Default sandbox for exec is **read-only** [D].

### Event schema

Docs [D]: event types are `thread.started`, `turn.started`, `turn.completed`, `turn.failed`, `item.started` / `item.updated` / `item.completed`, and `error`. Item types are `agent_message`, `reasoning`, `command_execution`, `file_change`, `mcp_tool_call`, `web_search`, and plan/todo updates (`todo_list`).

Real sample, call 1 [V] (about 4 s wall time):
```jsonl
{"type":"thread.started","thread_id":"01a17e17-3feb-7953-91f6-8d427aeb2668"}
{"type":"turn.started"}
{"type":"item.completed","item":{"id":"item_0","type":"agent_message","text":"ok"}}
{"type":"turn.completed","usage":{"input_tokens":15032,"cached_input_tokens":12032,"cache_write_input_tokens":0,"output_tokens":5,"reasoning_output_tokens":0}}
```

Real sample, call 2: resume + command [V]:
```jsonl
{"type":"thread.started","thread_id":"01a17e17-3feb-7953-91f6-8d427aeb2668"}
{"type":"turn.started"}
{"type":"item.completed","item":{"id":"item_0","type":"agent_message","text":"I replied “ok.” I’ll now copy ..."}}
{"type":"item.started","item":{"id":"item_2","type":"command_execution","command":"/bin/zsh -lc 'cat a.txt'","aggregated_output":"","exit_code":null,"status":"in_progress"}}
{"type":"item.completed","item":{"id":"item_2","type":"command_execution","command":"/bin/zsh -lc 'cat a.txt'","aggregated_output":"hi\n","exit_code":0,"status":"completed"}}
{"type":"item.completed","item":{"id":"item_3","type":"agent_message","text":"... writing it to b.txt was blocked because the workspace is read-only."}}
{"type":"turn.completed","usage":{"input_tokens":45791,"cached_input_tokens":44800,...,"output_tokens":321,"reasoning_output_tokens":29}}
```

Observations:
- `thread_id` is the session id that you pass to `resume`.
- `usage` is cumulative for the turn.
- The model's attempted write (blocked by the sandbox) did **not** surface as a `file_change` item. Only successful or approved items appear.
- There are no token deltas in exec JSON. For streaming text, use the app-server (`item/agentMessage/delta`).
- Baseline overhead is about 15k input tokens per fresh thread (system, skills and plugin instructions). Most of it is cached.

## 2. Sessions, resume and handover

### Commands [V]

- `codex exec resume <SESSION_ID|thread-name> [PROMPT]` or `codex exec resume --last [--all]`. `--all` disables the cwd filtering of `--last`.
- `codex exec fork <SESSION_ID> [PROMPT]` branches a session into a new id.
- Also available: `codex archive|unarchive|delete <id>` and `codex migrate-rollouts`.
- **Resume does not accept `-s/--sandbox`**. The resumed session kept the original **read-only** sandbox [V]. You can override with `-c sandbox_mode=...` (untested), or use app-server `thread/resume` with its `sandbox` and `approvalPolicy` params [V schema].

### Rollout storage [V]

- Path: `~/.codex/sessions/YYYY/MM/DD/rollout-<ISO-time>-<thread_id>.jsonl`
- Index: `~/.codex/session_index.jsonl` (`{id, thread_name, updated_at}`)
- There are also many sqlite stores (`state_5.sqlite`, `thread_history_1.sqlite`, ...). The rollout format is migrating to "paginated thread history" (`codex migrate-rollouts`). **Treat rollout files as an internal, unstable format.**

Each rollout line is `{timestamp, ordinal, type, payload}`. The `type` is one of:
- `session_meta`: id, cwd, ...
- `turn_context`: cwd, workspace roots, sandbox, model
- `world_state`
- `response_item`: raw OpenAI **Responses API items**, such as `message` (roles developer/user/assistant), `reasoning` (with **encrypted_content**), `custom_tool_call` / `_output`, and function calls
- `event_msg`: `task_started`, `item_completed`, `token_count`, `task_complete`, `thread_settings_applied` (model `gpt-5.6-sol`, provider `openai`, approval_policy, ...)

### Injecting history from another tool

**Yes. Use app-server `thread/inject_items`** [V real call]:
- Params: `{threadId, items: [<raw Responses API items>]}`. It "appends raw Responses API items to the thread's model-visible history without starting a user turn" [D].
- Test: I injected a user and an assistant message stating "the codename is PINEAPPLE-7". The next `turn/start` asked for the codename, and the model answered `PINEAPPLE-7`. The response to `thread/inject_items` was `{}`.
- Item shapes that worked:
  ```json
  {"type":"message","role":"user","content":[{"type":"input_text","text":"..."}]}
  {"type":"message","role":"assistant","content":[{"type":"output_text","text":"..."}]}
  ```
- In principle you can also inject `function_call` / `function_call_output` pairs for prior tool calls. That is untested, and it is safer to flatten foreign tool calls to text.

**Alternatives:**
- Pass `developerInstructions` (or `baseInstructions`) on `thread/start` / `thread/resume` with a summarized transcript [V schema].
- In exec mode, prepend a "conversation so far" block to the prompt, or pipe the transcript via stdin (it becomes a `<stdin>` block).
- Hand-writing a rollout file and then calling `exec resume` is possible but fragile, because the format is internal and migrating. Not recommended.

**Codex can already import Claude Code sessions natively** [V]:
- `~/.codex/external_agent_session_imports.json` on this Mac lists imported `~/.claude/projects/*.jsonl` files mapped to `imported_thread_id`s.
- The app-server exposes this as `externalAgentConfig/detect`, `externalAgentConfig/import`, `externalAgentConfig/import/readHistories` and `externalAgentConfig/import/recordHistory`, plus `.../progress` and `.../completed` notifications [V schema, D].
- It is designed as a one-shot migration UX (AGENTS.md, config, skills, plugins, hooks, sessions), not live switching. It's still useful as a reference for how OpenAI maps Claude transcripts.

**Recommendation:** oxbot owns the canonical transcript. On a switch to Codex, call `thread/start`, then `thread/inject_items` (the canonical turns converted to Responses items, with the tail verbatim and older parts summarized), then `turn/start`.
- Keep the Codex `threadId` mapped to the oxbot conversation, so consecutive Codex turns reuse the native thread and only the delta needs injecting.
- On a switch away, read Codex items from the stream (or `thread/read`) into the canonical transcript.
- **Reasoning items are encrypted and Codex-only.** Never try to carry them across backends.

## 3. Embedding protocols

### `codex app-server` (recommended route for oxbot)

What the docs say [D] https://learn.chatgpt.com/docs/app-server (formerly developers.openai.com/codex/app-server):
- It is the interface behind the VS Code extension and the Desktop app. Use it for "a deep integration inside your own product".
- For CI or automation, they point to the Codex SDK and `exec` instead.
- The command is still labelled **[experimental]**, and the WebSocket transport is "not supported for production".

Transport:
- `--listen stdio://` (default), `unix://PATH`, `ws://IP:PORT`, or `off`.
- WebSocket auth options: `--ws-auth capability-token|signed-bearer-token`. Non-loopback WebSocket listeners are **unauthenticated by default**.
- There is also `codex app-server daemon` / `proxy`, plus `codex remote-control`.

Wire format: JSON-RPC 2.0 **without the `"jsonrpc"` field**, as newline-delimited JSON.

Handshake: `initialize {clientInfo:{name,title,version}, capabilities?:{experimentalApi, optOutNotificationMethods, ...}}`, then the `initialized` notification. Requests before the handshake get "Not initialized".

Methods (95 client requests) [V, generated schema]. The ones oxbot needs:
- Threads: `thread/start` (cwd, model, modelProvider, sandbox, approvalPolicy, approvalsReviewer, baseInstructions, developerInstructions, ephemeral, config), `thread/resume`, `thread/fork`, `thread/read`, `thread/list`, `thread/rollback`, `thread/compact/start`, `thread/inject_items`, `thread/archive`
- Turns: `turn/start` (threadId, input[text|image|localImage|...], plus per-turn overrides for cwd, model, effort, sandboxPolicy, approvalPolicy, outputSchema), `turn/steer` (adds input mid-turn; needs `expectedTurnId`), `turn/interrupt` (threadId, turnId)
- Other: `model/list`, `account/read`, `account/rateLimits/read`, `config/read`, `config/value/write`, `command/exec*`, `fs/*`, `mcpServerStatus/list`
- Experimental, gated by `capabilities.experimentalApi`: `dynamicTools` on `thread/start`. These are oxbot-provided tools; Codex calls back with the server request `item/tool/call` (`DynamicToolCallParams {threadId, turnId, callId, tool, namespace, arguments}`).

Notifications (72): `thread/started`, `thread/status/changed`, `turn/started`, `turn/completed`, `turn/diff/updated`, `turn/plan/updated`, `item/started`, `item/completed`, `item/agentMessage/delta`, `item/reasoning/*Delta`, `item/commandExecution/outputDelta`, `item/fileChange/patchUpdated`, `thread/tokenUsage/updated`, `account/rateLimits/updated`, `mcpServer/startupStatus/updated`, `warning`, `error`, and more.

Server→client requests (approvals):
- `item/commandExecution/requestApproval`. Decisions: `accept | acceptForSession | acceptWithExecpolicyAmendment{...} | decline | cancel`.
- `item/fileChange/requestApproval`. Decisions: `accept | acceptForSession | decline | cancel`. `cancel` also interrupts the turn.
- `item/permissions/requestApproval`: network or filesystem grants.
- `item/tool/requestUserInput`, `mcpServer/elicitation/request`, `item/tool/call`, `account/chatgptAuthTokens/refresh`
- Each request is followed by `serverRequest/resolved` and then `item/completed` [D].

Observed in the real run [V]:
- **I did not receive `turn/completed` within 120 s.** The last events were `thread/tokenUsage/updated`, `account/rateLimits/updated`, then `thread/status/changed {type:"idle"}`. The cause is unknown; it might relate to the ephemeral thread or the timing of my reader.
- oxbot should treat `thread/status/changed → idle` as a completion signal too, and test this before relying on it.

Type bindings:
- `codex app-server generate-json-schema --out DIR` / `generate-ts` produce **version-matched** schemas [V]. For Rust, generate types from the JSON Schema (`typify`), or depend on the `codex-app-server-protocol` crate via **git** from `openai/codex` (`codex-rs/app-server-protocol`), pinned to the installed CLI tag.
- The crates.io crate `codex-app-server-protocol` (0.63.0) is published by a **third-party fork** (namastexlabs) and is stale. Don't use it.

### `codex mcp-server` [V help]

- Exposes Codex as an MCP server over stdio. Historically it offers tools `codex` and `codex-reply`.
- It is coarse (one tool call per turn) and approvals come back as MCP elicitations. It is fine for "Codex as a tool of another agent", but worse than app-server for a chat UI.
- **`codex proto` no longer exists** in 0.148. app-server replaced it.

### ACP (Agent Client Protocol, Zed)

The Codex adapter:
- The official adapter moved from `zed-industries/codex-acp` to **`agentclientprotocol/codex-acp`** (Apache-2.0, TypeScript/Node). The new one **wraps `codex app-server`** and translates ACP↔app-server. Run it with `npx -y @agentclientprotocol/codex-acp`. Auth is ChatGPT, `CODEX_API_KEY`/`OPENAI_API_KEY`, or a custom gateway. It supports images, permissions, MCP, plans, token usage and slash commands.
- Sources: https://github.com/agentclientprotocol/codex-acp, https://zed.dev/acp/agent/codex, https://zed.dev/docs/ai/external-agents

Rust crates (crates.io, as of 2026-10-22):
- `agent-client-protocol` 3.5.0 (about 5.6M downloads)
- `agent-client-protocol-schema` 1.12.0
- `agent-client-protocol-tokio` 0.11.1
- `agent-client-protocol-rmcp`

Claude Code also has an ACP adapter (Zed's `claude-code-acp` / `@zed-industries/claude-agent-acp`). That is out of scope here; verify it in the Claude research.

Is ACP a good uniform protocol for oxbot?
- **Pros:** one client implementation, a Rust crate, and session/prompt/permission/tool-call events normalized across agents.
- **Cons:**
  1. It adds a Node adapter process per backend. That is an extra hop and an extra dependency, though only a local one.
  2. It is a lowest common denominator. You lose `thread/inject_items`, `turn/steer`, rollback/fork, rate limits and dynamic tools unless you use extensions.
  3. ACP sessions are agent-owned. Injecting a foreign transcript is not a first-class ACP operation; note that the `agentkit-acp` fork exists precisely to add "session injection".
  4. OpenRouter (your own loop) would need oxbot to implement the agent side anyway.
- **Verdict:** use native app-server for Codex (thin JSON-RPC, small surface, and it gives the injection hook). Optionally design oxbot's internal backend trait to resemble ACP's session/update model so an ACP backend can be added later.

## 4. Sandbox, approvals, auth and providers

### Sandbox [V help, D agent-approvals-security]

- `-s read-only | workspace-write | danger-full-access`.
- On macOS this is Seatbelt (`sandbox-exec`). **Network is off by default** in the sandbox.
- `[sandbox_workspace_write] network_access = false` (keep it false).
- Writable extras: `--add-dir`, `sandbox_workspace_write.writable_roots`. `exclude_tmpdir_env_var` and `exclude_slash_tmp` are available.
- `.git`, `.agents`, `.codex` and `.aws` stay read-only even inside writable roots.
- The optional `features.network_proxy` with a `domains` allow/deny list gives per-domain egress (experimental, off by default).
- `-C/--cd <DIR>` sets the working root, and `--skip-git-repo-check` allows non-git directories.

### Approvals

- `approval_policy = "untrusted" | "on-request" | "never" | {granular = {sandbox_approval, rules, mcp_elicitations, request_permissions, skill_approval}}`. The config reference says `untrusted` is unsupported in config and `on-failure` is deprecated.
- `--approve-for-me` / `approvals_reviewer` route approvals to an automatic "guardian" model review. That review is another model call to OpenAI.
- For **unattended oxbot**, use either:
  - `sandbox=workspace-write` + `approvalPolicy=never` (failures go back to the model), or
  - `on-request`, with oxbot answering `requestApproval` server requests itself, via policy or by forwarding to the user's phone/UI.
- Never use `danger-full-access` or `--yolo`. That also flips `web_search` to `live`.

### Auth [V]

- `codex login` (ChatGPT, browser or `--device-auth`), `codex login --with-api-key` (stdin), `--with-access-token`, and `codex login status`. This machine shows "Logged in using ChatGPT".
- The env var `CODEX_API_KEY` works for exec (set it per process only) [D].
- Credentials live in `$CODEX_HOME/auth.json` (not read). There is `cli_auth_credentials_store` / `secret_auth_storage`, a feature that is off by default.
- With a ChatGPT login, usage counts against the plan's 5-hour and weekly limits. The app-server reports these via `account/rateLimits/updated`, for example `planType: "plus"`, `windowDurationMins: 300 / 10080`.

### Local models [D config-advanced, config-reference]

- `--oss` with `--local-provider ollama|lmstudio`, or `oss_provider = "ollama"` in config. exec errors if this is unset.
- Or a custom provider:
  ```toml
  [model_providers.lan]
  name = "LAN"
  base_url = "http://192.168.x.y:11434/v1"
  wire_api = "responses"
  ```
- **`wire_api = "responses"` is the only supported value now.** Chat Completions was removed around February 2026 [3P]. A local server must therefore speak the **OpenAI Responses API**. Recent Ollama and LM Studio do; vLLM and llama.cpp support varies.
- Reserved provider IDs are `openai`, `ollama` and `lmstudio`. `model_provider` and `model_providers` can't be set in project-local config.
- With a local provider, prompts and inference stay on the LAN. **Other egress still exists**, such as telemetry, update checks, plugins and apps (see section 5), unless you disable it.

### OpenRouter

- Technically possible:
  ```toml
  [model_providers.openrouter]
  base_url = "https://openrouter.ai/api/v1"
  env_key = "OPENROUTER_API_KEY"
  wire_api = "responses"
  ```
  Source: https://openrouter.ai/blog/tutorials/codex-cli-openrouter/
- **This violates the new constraint** (only Anthropic and OpenAI may receive data), so don't offer it for the Codex backend.

## 5. Cancel/interrupt, and what leaves the machine

### Cancel / interrupt

- **app-server:** `turn/interrupt {threadId, turnId}` returns `{}`. The turn ends with `turn/completed` `status:"interrupted"`, and pending approval or user-input requests are cleared with `serverRequest/resolved` [D]. A file-change `cancel` decision also interrupts the turn. `turn/steer` redirects a running turn without cancelling it.
- **exec:** there is no protocol-level cancel. Send SIGINT or SIGTERM to the child process; kill the whole process group, because commands run in child shells. Because rollouts are persisted incrementally, `exec resume` should continue afterwards (not tested).
- **Background shells:** these use `unified_exec`, with `background_terminal_max_timeout` defaulting to 300000 ms. Make sure the process group is killed on oxbot shutdown.

### Recommended locked-down config for oxbot

Put this in a dedicated `CODEX_HOME=~/.oxbot/codex/config.toml`, or pass each line as `-c` overrides:

```toml
model_provider = "openai"
approval_policy = "never"          # or "on-request" + oxbot answers approvals
sandbox_mode = "workspace-write"
web_search = "disabled"
check_for_update_on_startup = false
hide_agent_reasoning = false
[sandbox_workspace_write]
network_access = false
[analytics]
enabled = false
[feedback]
enabled = false
[otel]
exporter = "none"
trace_exporter = "none"
metrics_exporter = "none"
log_user_prompt = false
[history]
persistence = "none"               # optional; rollouts still saved unless ephemeral
[features]
apps = false
plugins = false
remote_plugin = false
skill_mcp_dependency_install = false
computer_use = false
browser_use = false
in_app_browser = false
image_generation = false
memories = false
in_app_updates = false
[shell_environment_policy]
inherit = "core"                   # don't leak oxbot's env (API keys) into agent shells
```

Caveats on this config:
- A separate `CODEX_HOME` needs its own `codex login` (its own `auth.json`). The alternative is `--ignore-user-config` (exec only) plus `-c` overrides, which keeps the existing auth.
- Run `codex features list` with the new home to confirm every flag is off.
- **Verify egress empirically:** run oxbot's Codex under Little Snitch / LuLu, or `nettop -p <pid>`, and confirm only `chatgpt.com`, `auth.openai.com`, and `api.openai.com` (and possibly `ab.chatgpt.com`) appear.

**Data retention:** under a ChatGPT login, data handling follows the ChatGPT plan's data controls. On Plus/Pro, the "Improve the model for everyone" setting applies to Codex. Business/Enterprise and the API are not used for training by default, and API customers can get ZDR. I could not fetch an official page confirming the exact Codex wording in this run, so check https://learn.chatgpt.com (Codex FAQ / data controls) and the user's ChatGPT data-control settings.

## Recommended integration for oxbot (Codex backend)

1. **Spawn one long-lived `codex app-server --listen stdio://` child per oxbot process.**
   - Set `CODEX_HOME` to the locked-down home and `stdin`/`stdout` to pipes.
   - Speak line-delimited JSON-RPC (no `jsonrpc` field) with tokio: a `BufReader::lines()` reader task, plus a pending-request map keyed by `id`.
   - Generate Rust types from `codex app-server generate-json-schema` at build time, or git-depend on `openai/codex` `codex-rs/app-server-protocol` pinned to the CLI version. Check the version in `initialize` → `userAgent` and refuse on mismatch.
2. **Per oxbot conversation:**
   - Call `thread/start {cwd, sandbox:"workspace-write", approvalPolicy, model, developerInstructions}`, then `thread/inject_items` with the canonical history converted to Responses `message` items, then `turn/start`.
   - Stream `item/agentMessage/delta` to the UI. Persist `item/completed` items into the canonical transcript. Stop on `turn/completed`, or on `thread/status/changed:idle` as a fallback.
3. **Approvals:** handle `item/commandExecution/requestApproval` and `item/fileChange/requestApproval` with oxbot policy or a user prompt. Always reply, or the turn hangs.
4. **Cancel:** `turn/interrupt`. **Steer:** `turn/steer`. **Switch away:** keep the threadId. **Switch back:** inject only the turns since the last Codex turn.
5. **Fallback / simple mode:** `codex exec --json -C <dir> -s workspace-write --skip-git-repo-check -c approval_policy="never" ... </dev/null`, parsing the JSONL. Use it for one-shot jobs.

## Open risks

- app-server is labelled **experimental**. The protocol churns fast (95 methods; v1/v2 schemas; removed features). Pin the CLI version and regenerate types on upgrade, and switch off auto-update (Homebrew/npm) for the oxbot machine.
- `turn/completed` wasn't observed in my probe. Investigate before relying on it.
- About 15k tokens of Codex system/skills/plugin overhead per thread. Disabling plugins and skills should shrink it.
- Rollout and sqlite storage formats are internal and migrating. Don't parse them; use `thread/read`.
- Injected history counts as input tokens on every Codex turn, so summarize long histories.
- Reasoning items are encrypted and backend-specific.
- ChatGPT-plan rate limits (5 h / weekly) apply to an always-on bot. Surface `account/rateLimits/updated`.
- Non-OpenAI egress (GitHub update checks, plugin marketplace, CDNs, connectors, live web search, agent shell network) exists by default. It is all switchable (see the table above) but must be verified with a firewall.
- OpenRouter as a Codex provider conflicts with the "Anthropic/OpenAI only" rule.
- A local model needs a Responses-API-compatible server.
